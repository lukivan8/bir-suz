# Локальная проверка расширения

Цель: доказать, что **изменённый код работает в установленном расширении**, а не только собирается.

## Один раз

1. Используйте отдельный тестовый профиль Chrome или согласованную тестовую установку. Не очищайте storage и не удаляйте пользовательское расширение.
2. В `chrome://extensions` включите Developer mode и загрузите **Load unpacked → `/Users/lukivan8/dev/bir-soz-workspace/bir-suz/dist`** после сборки.
3. В Details проверьте **Loaded from** и запишите ID этой установки. В другом checkout ID может отличаться. `~/dev/bir-suz/dist` — другая сборка, её Reload не обновляет workspace!
4. При первом запуске аналитика выключена по умолчанию; оставьте её выключенной. Обычный UI smoke не должен отправлять тестовую аналитику на Perry. Пользовательский consent не меняйте.

## После каждой правки

```bash
cd /Users/lukivan8/dev/bir-soz-workspace/bir-suz
# Только при первом запуске или изменении lockfile:
npm ci
npm run lint
npm run build
```

Нужен Node.js >=22. Если `node`/`npm` отсутствуют, найдите доступный runtime; не меняйте package/lockfile ради окружения. В Codex можно использовать `load_workspace_dependencies`.

1. До правки зафиксируйте ожидаемый результат: например, прежний и новый текст кнопки.
2. После успешной сборки откройте `chrome://extensions/?id=<ID>` и нажмите **Reload именно у Bir Söz**. Дождитесь `Reloaded`. Обновление обычной вкладки этого не заменяет.
3. Закройте и заново откройте popup. Обновите вкладку прогресса и обычную тестовую страницу: старые content scripts после Reload могут потерять связь с расширением.
4. Проверьте изменение в UI. Наличие текста в `dist` или успешный build сами по себе не доказательство.
5. Пройдите короткий smoke ниже. В ответе укажите, что изменилось и что реально увидели.

`npm run dev`/Vite preview не заменяют этот цикл. `dist/` генерируется, не редактируется вручную и не коммитится. Менять manifest version ради каждой локальной проверки не нужно.

## Smoke за пару минут

- **Popup:** откройте через значок расширения; проверьте новый текст, настройки и отсутствие обрезки элементов.
- **Прогресс:** нажмите «Мой прогресс»; страница открывается, настройки и SRS сохраняются после обновления.
- **Задание:** откройте/обновите `https://example.com`, затем в popup нажмите «Показать пример задания». Закройте popup, если он остался открыт. Выберите ответ; повторите показ и нажмите «Пропустить». Overlay должен закрыться, страница остаться рабочей.
- **Ошибки:** проверьте Errors на карточке расширения, Console service worker (Inspect views), Console popup/dashboard и тестовой страницы. Ошибки, уже существовавшие до проверки, отделяйте от новых; не скрывайте их очисткой.

`chrome://`, Chrome Web Store и страница самого расширения не подходят для Demo Trigger. `chrome-extension://<ID>/index.html` удобен для проверки разметки popup, но для показа задания нужен **настоящий popup над обычной HTTP(S)-вкладкой**.

Для проверки аналитики используйте локальный backend с временной SQLite и отдельную тестовую конфигурацию API. Не включайте production-статистику ради UI smoke. Не выводите storage целиком, UUID, коды или payload в отчёт.

## Если изменение не видно

Проверьте по порядку: правильный checkout → успешный build → Loaded from у нужного ID → Reload расширения → повторное открытие popup → обновление тестовой страницы. Не лечите это удалением расширения: так можно потерять SRS и настройки.

Агент может пройти шаги через доступный browser tool; для `chrome://extensions`, выбора папки и настоящего popup подходит native Chrome через `cua_repl`. Читайте свежий accessibility state после действий. Не используйте ID элементов из прошлого прогона. В macOS-диалоге выбора папки: Cmd+Shift+G → вставить полный путь → Enter → Select.

После проверки отключите только созданную вами дополнительную тестовую копию, если она иначе дублирует рабочее расширение. Не удаляйте её storage. Пользовательские вкладки и установку оставьте как были.

## Изолированный локальный API

Для HTTP-интеграции используйте временную SQLite и явно отключённый импорт:

```bash
cd ../bir-stats
DB_PATH=/tmp/bir-soz-managed-integration.sqlite SQLITE_MIGRATE_PATH='' PORT=4017 bun run src/index.ts
```

Тестовая сборка создаётся отдельно от основной:

```bash
VITE_BIR_API_ORIGIN=http://127.0.0.1:4017 npm run build -- --outDir /tmp/bir-soz-managed-test --emptyOutDir
```

Переменная задаётся только во время сборки. Manifest получает только выбранный
API origin. Обычная `npm run build` сохраняет production API permission.
Отключите основную копию на время работы тестовой на тех же страницах; по окончании
выключите тестовую и включите основную. Не переносите storage между ними.

## Автоматические проверки контракта и HTTP

Нужен соседний checkout `../bir-stats` с установленными зависимостями и Bun1.3.13:

```bash
npm test
npm run test:http
```

`npm test` включает HTTP-тест. Он сам выбирает локальный порт, создаёт временную
SQLite, запускает отдельный процесс backend, проверяет каталог/ETag/организацию,
XLSX/remote merge/SRS, analytics/часы/dedup и повторный старт. В finally процесс
останавливается, созданная временная директория удаляется. Перенос базы явно
отключён через `SQLITE_MIGRATE_PATH=''`. Production API/SQLite не используются.
CI расширения проверяет оба проекта и идентичность contract fixtures/schemas.
